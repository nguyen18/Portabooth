# Portabooth — Architecture & Context

Deep-dive reference for future sessions/agents working on this repo. Read this before making changes so you don't have to re-derive context from scratch.

## What this project is

A browser-based photobooth ("Portabooth" — formerly named "Snapstrip" in-app; renamed 2026-09-14 to match the repo/product name). User taps a button, the browser's webcam captures 4 photos on a countdown timer, and the shots are composited into a single vertical photo-strip image (like a real photobooth strip) that can be saved, shared, or printed.

**Everything happens client-side.** No backend, no server, no build step, no dependencies. The camera feed and captured images never leave the device — there is nothing to upload to.

## Current state

- `index.html` — markup and JS (a single `<script>` block); CSS lives in `style.css`, linked via `<link rel="stylesheet">` (split out 2026-09-16 — see "Working conventions" below for why JS stayed inline). Named `index.html` (renamed from `photobooth.html` 2026-09-14) so GitHub Pages serves it as the site root.
- `style.css` — all page styling (site themes, layout, print CSS), previously an inline `<style>` block in `index.html`.
- `CNAME` — custom domain (`portabooth.studio`) for GitHub Pages.
- `qrcode.min.js` — vendored third-party QR code generator (davidshimjs/qrcodejs, MIT), loaded via a local `<script src>` tag. See "Custom template sharing" below for why it's vendored instead of a CDN `<script>` tag.
- `fonts/Unna-{Regular,Bold,Italic,BoldItalic}.ttf` — vendored Unna typeface (SIL Open Font License, `fonts/Unna-OFL.txt`), used for the caption/date drawn onto the exported strip. Vendored for the same reason as the QR library: no third-party dependency at runtime.
- `sounds/shutter.mp3` — vendored camera-shutter sound effect (user-supplied download, ~1s, no license file included alongside it — unlike the font/QR library, there's no bundled license text to point to if this is ever redistributed beyond this repo), played on each shot.
- `sounds/lofi-loop.mp3` — vendored background music loop (user-supplied download, ~22s, same no-license-file caveat as the shutter sound), looped on every page — see "Background music" below.
- `favicon.ico`, `icons/favicon-{16x16,32x32}.png`, `icons/apple-touch-icon.png` — favicon, generated from a user-supplied camera icon (`pikura-cam-9342564_1920.png`, cropped to content and padded to a square). Regenerate all four from the same source if the icon ever changes, don't hand-edit the small sizes independently.
- `README.md` — one-line project blurb.
- No package.json, no framework, no bundler. Opening the HTML file in a browser (or serving it statically) is the whole deploy story.
- Deployed via GitHub Pages, custom domain `portabooth.studio` (DNS managed in Squarespace Domains, pointed at GitHub's Pages IPs/host). Pushing to `main` redeploys automatically — no CI step needed.

Deliberate choice, not a placeholder: [conversation with the project owner](.) concluded plain HTML/vanilla JS is the right call here over React — the app is a single screen with no routing, state is a handful of DOM refs + one `shots` array, and it uses browser APIs (`getUserMedia`, `<canvas>`, Web Share) directly, which a framework wouldn't simplify. A framework would only earn its cost if this grows multiple screens/routes or shared state across views. See "If this grows" below.

## Architecture of `index.html`

### Layout (HTML)
- `#templateNote` — one-line "Using a shared custom template" indicator, shown only when the page was opened via a link/QR that encodes a saved template (see below).
- `#bgMusic` (`<audio loop>`) / `#musicToggle` — background music loop and its on/off toggle button, shown/active on every page (main page and shared template links alike) — see "Background music" below.
- `.customize` (`<details open>`) — the template editor: site-theme `<select>`, caption `<input>`, Bold/Italic style checkboxes, show-date checkbox, a live `#captionPreview` canvas, and the "Get shareable link" flow (link `<input readonly>` + copy button + `#qrOutput` QR code container). Expanded by default (`open` attribute) so a first-time visitor lands on customization, not the camera — still collapsible via the `<summary>`. Hidden entirely for shared-link recipients regardless of `open`, via `customizeDetails.style.display = 'none'` (see "Custom template sharing" below).
- `.stage` — the live camera view: `<video>` element (mirrored front camera feed), flash overlay, countdown overlay, shot counter (`0 / 4` etc.), and the Start/Retake buttons.
- `#permHint` — camera-permission helper text shown before capture / on `getUserMedia` failure.
- `.strip-wrap` — the result screen: rendered photo strip (`<canvas id="stripCanvas">`), a `.field-row` pairing `#dateStyleField` (date-format `<select>`: `'long'` / `'numeric'` / `'off'` — only visible once a strip exists and `config.showDate` is true; `'off'` hides the date without touching the locked `config.showDate`, see "Recipient lockdown" below) with `#filterSelect` (photo filter: `'default'` / `'bw'` / `'sepia'`, see "Photo filter" below), and the Save / Share / Print / New-strip buttons. Hidden until a session completes. The caption/date text is drawn directly onto the canvas (not a separate DOM overlay) so it's included in Save/Share output — see "Custom template sharing" below. `#stripCanvas` itself has no cut-guide border; that only exists on the separate print-formatting canvas (`buildPrintCanvas()`, see "Print layout" below).
- `#workCanvas` — declared but currently **unused / dead** (see Known issues below).

### Styling
`style.css` (linked from `<head>`, not inline — see "Current state" above). Two independent color systems, which was a point of real confusion during development and is worth keeping straight:
- **Site theme** — CSS custom properties for the "velvet curtain photobooth" *page chrome* (`--curtain`, `--bulb`, `--brass`, etc.), defined on `:root` and overridden via `:root[data-theme="noir|blush|mint|sanrio"]`. Controlled by the "Site theme" select. Does **not** affect the exported strip. `sanrio` is an original pastel-pink/kawaii-coded palette (raspberry curtain, near-white bow-colored glow) — not any actual Sanrio artwork, logo, or character, which would be a licensing issue; it's a color theme "in that vein," same as how `blush`/`mint` aren't tied to a specific brand.
- **Strip appearance** — always plain white paper with dark ink (`STRIP_PAPER`/`STRIP_INK` constants in JS), regardless of site theme, so a printed strip always looks like a real photobooth strip. `.strip-frame` background is hardcoded `#ffffff` for the same reason.

Four `@font-face` declarations load the vendored Unna weights/styles (regular/bold/italic/bold-italic) for the canvas-drawn caption. Includes a `@media print` rule, used only on desktop — see "Print layout" below for why mobile takes a different path entirely.

### JS (single `<script>` block)
No modules, no classes — a flat script with DOM refs at the top and a handful of functions:

| Function | Responsibility |
|---|---|
| `initCamera()` | Calls `startCamera(facingMode)` (starts on the front camera), then `enumerateDevices()` to check for more than one `videoinput` — `#flipCameraBtn` only becomes visible if a second camera actually exists (most laptops only have one). Runs immediately on page load. |
| `startCamera(mode)` | Requests `getUserMedia` with the given `facingMode` (ideal 1280×960). Only stops the previous stream's tracks and commits `facingMode`/`video.classList('mirrored')` once the new stream has actually succeeded — a failed camera switch leaves the working camera running rather than blanking the viewfinder. Shows `permHint` text on failure. |
| `runCountdown(seconds)` | Async, updates `#countdown` overlay text once per second via `sleep()`. |
| `doFlash()` | CSS-opacity flash effect on `.flash` overlay plus `playShutterSound()`, triggered right before each capture. Uses a forced reflow (`void flashEl.offsetHeight`) between the "flash on" and fade-out style writes — without it, the two changes could get coalesced into a single paint and the flash would inconsistently fail to render. |
| `playShutterSound()` | Plays the vendored `sounds/shutter.mp3` via the shared `shutterAudio` (`HTMLAudioElement`), resetting `currentTime` first so rapid repeats restart cleanly. |
| `captureFrame()` | Grabs one frame from `<video>` onto an off-DOM `<canvas>`, cover-fit-cropped to a fixed 500×375 (4:3) cell. Mirrored to match the on-screen preview only when `facingMode === 'user'` — the back camera captures un-mirrored, like a real camera. Returns the canvas. |
| `buildStrip()` | Async. Calls `drawStripContent()` to render one strip onto `#stripCanvas` — used for the on-screen preview and Save/Share. Deliberately has **no** cut-guide border (see `buildPrintCanvas()` below for where that lives instead) — a single saved/shared image isn't being cut apart from anything. |
| `drawStripContent(ctx, offsetX, stripW, photosH, layout)` | Draws one strip's paper background, photos (with `PHOTO_SCALE` and `applyPixelFilterMatrix()` applied per photo), and caption at a given x offset — no border. Shared by `buildStrip()` and `buildPrintCanvas()` so both stay in sync; the x offset is what lets `buildPrintCanvas()` draw two of these side by side on one wider canvas. |
| `buildPrintCanvas()` | Async. Sizes a canvas to fit the two-strip block *plus* `PRINT_TOP_MARGIN`/`PRINT_SIDE_MARGIN`/`PRINT_BOTTOM_MARGIN` of extra blank space around it, fills the whole thing paper-white, then `ctx.translate()`s so the two `drawStripContent()` calls (offsets `0` and `stripW`, unchanged) land inset by those margins from the canvas edge — see "Print layout" below for exactly what each margin measures. Draws the border **once** afterward: an outer dashed rectangle around the whole combined image plus one dashed line down the middle — this is the *only* place a cut-guide border is drawn anywhere in the app. |
| `renderCaptionPreview()` | Async. Draws the same caption/date band (via `computeCaptionLayout()` + `drawCaptionLines()`) onto the small `#captionPreview` canvas in the customize panel, at the same pixel width as the real strip so it's an exact preview, not an approximation. Called from `applyConfig()` and `onConfigFieldChange()` so it updates live as the user types/toggles, before any photo is taken. |
| `computeCaptionLayout()` / `drawCaptionLines(ctx, width, top, layout)` | Shared caption logic used by both `buildStrip()` and `renderCaptionPreview()`, so the live preview and the final export can never drift out of sync. `computeCaptionLayout()` returns `{captionLine, dateLine, captionH}` — when there's a caption but no date, `captionH` adds back the space a date line would have taken (as extra bottom padding) rather than shrinking, so turning the date off doesn't change the strip's overall exported/print size. `drawCaptionLines()` draws those two lines at a given vertical offset. |
| `captionFont(size)` | Builds a canvas `font` shorthand string (`italic bold 30px Unna, Georgia, serif`) from the current `config.bold`/`config.italic`, used both to draw text and to `document.fonts.load()` the right variant. |
| `loadCaptionFonts()` | Awaits `document.fonts.load()` for both caption/date sizes before any caption drawing — Unna must be loaded before `ctx.font` can use it, or canvas silently falls back to the default serif font. |
| `runSession()` | First unlocks `shutterAudio` synchronously (muted play-then-pause, no `await` before it) — iOS Safari specifically only allows a media element's first `play()` to succeed when called directly inside the click handler, not later inside an async chain. Muted so this priming call is silent — the real, audible shutter click only ever comes from `playShutterSound()` inside `doFlash()`, timed with the flash. Then orchestrates one full run: resets `shots`, loops 4× doing countdown → flash → capture, then `await`s `buildStrip()` and reveals the result screen. |
| Save/Share/Print handlers | `saveBtn` → tries the native share sheet first via `canShareFiles()`/`navigator.share` (see "Save to Photos" below), falling back to `downloadStripPng()` (a plain `canvas.toDataURL('image/png')` download link) when sharing isn't supported or genuinely fails. `shareBtn` → `navigator.share` with a `File` (only shown if `navigator.canShare` exists) — same underlying mechanism as `saveBtn`'s fallback path, kept as a separate labeled action for "share with someone" intent. `printBtn` ("Print") → async; platform-split (see "Print layout" below): shares `buildPrintCanvas()`'s combined two-strip image as a PNG via `navigator.share()` on mobile, or populates `#printSheet` and calls `window.print()` on desktop. `againBtn` → hides the result screen to shoot again. |
| `applySiteTheme(siteTheme)` / `applyConfig(cfg)` | Sets/removes `data-theme` on `<html>` (page chrome only) and syncs the customize form fields to a `config` object. |
| `encodeConfig(cfg)` / `decodeConfig(str)` / `readConfigFromURL()` | Pack/unpack `{siteTheme, caption, bold, italic, showDate}` to/from a base64-JSON `#c=` URL hash. `decodeConfig` validates `siteTheme` against the known list and clamps `caption` length — untrusted input, since it comes from a URL someone else generated. |
| `onConfigFieldChange()` | Fired on customize-field input/change; updates `config`, re-applies the site theme, updates `#dateStyleField` visibility, and re-runs `buildStrip()` live if a strip was already captured. |
| `renderQRCode(container, text)` | Renders a QR code via the vendored `QRCode` global, retrying increasing QR "type" (matrix size) until the payload fits — the library doesn't auto-size and throws on overflow otherwise. |
| `formatDate(date)` | Formats a `Date` per the current `dateStyle` (`'long'` → "Sep 14, 2026", `'numeric'` → "9.14.26"). Not called at all when `dateStyle === 'off'` — `computeCaptionLayout()` short-circuits to an empty `dateLine` in that case. |

**State** is minimal and intentionally not framework-managed: `stream` (MediaStream), `facingMode` (`'user' | 'environment'`, which camera is active — not part of `config`/the shared URL, purely a local device choice), `shots` (array of captured `<canvas>` elements), `config` (`{siteTheme, caption, bold, italic, showDate}` — the shared/lockable template), `dateStyle` (`'long' | 'numeric' | 'off'`, **not** part of `config`/the shared URL — see below), and `photoFilter` (`'default' | 'bw' | 'sepia'`, likewise not part of `config` — see "Photo filter" below), all module-level `let` variables closed over by the functions above.

**Constants** controlling capture geometry: `SHOT_COUNT = 4`, `FRAME_W/FRAME_H = 500×375` (4:3), `PADDING = 30` (outer margin around the photos — the "cut to size" white border), `GAP = 14` (between photos), `PHOTO_SCALE = 0.99` (each photo is drawn at 99% of its cell size, both dimensions scaled equally so the diagonal shrinks by the same percentage, and centered within the cell — a subtle ~2.5px paper-colored border around each individual photo, distinct from and inside the outer `PADDING` margin). Caption layout: `CAPTION_FONT_SIZE = 32`, `DATE_FONT_SIZE = 22`, `CAPTION_LINE_GAP = 10`, `CAPTION_PAD = 18` (the caption band height is computed from these based on which of caption/date are actually present, not a fixed constant).

### Custom template sharing

Feature: a user can set a site theme, caption (with bold/italic styling), and date visibility, then get a link/QR code that reproduces that exact template for whoever opens it — no login, no per-user frame upload.

Design choice (discussed with the project owner before building): **entirely static, config packed into the URL** rather than adding any backend/storage. Concretely: `{siteTheme, caption, bold, italic, showDate}` → `JSON.stringify` → UTF-8-safe base64 → `#c=<blob>` URL hash → QR code generated client-side from that URL via the vendored `qrcode.min.js`. Opening the link re-decodes the hash and calls `applyConfig()` before the user does anything else.

This was chosen over two heavier alternatives (still on the table if requirements grow):
- **Full accounts** — login + per-user frame management. Rejected as overkill for "share one template with someone."
- **Minimal serverless storage** — real image upload, stored server-side under a short ID. Would be needed if arbitrary custom frame *graphics* (not just theme/caption) become a requirement, since an uploaded image can't reasonably live inside a URL/QR code. This is the natural next step if that's ever wanted — see the conversation history around 2026-09-14 for the fuller tradeoff writeup.

Because of this choice, current "frames" are limited to the built-in `SITE_THEMES` list (`classic`, `noir`, `blush`, `mint`, `sanrio`) plus free-text caption/style and a date toggle — not arbitrary uploaded graphics. Keep the encoded payload small (short strings/booleans only) so the QR code stays scannable.

`qrcode.min.js` is vendored (copied into the repo) rather than loaded from a CDN `<script src>` specifically to preserve the app's "everything runs on your device, no network dependency beyond the camera" property — a CDN script would make template rendering depend on a third party being up.

**Recipient lockdown.** When the page is opened via a shared link (i.e. `readConfigFromURL()` returns a config), `#customize` is hidden entirely (`customizeDetails.style.display = 'none'`) — the recipient gets the creator's theme/caption/style/date-visibility exactly as set, with no UI path to change any of it, including the caption. The one exception is **date format** (`'long'` / `'numeric'` / `'off'`, via `#dateStyleField`/`dateStyle`): this is deliberately kept *outside* `config`/the shared URL, so it's a free choice for whoever is using the page — creator or recipient — available once a strip has been captured, including the ability to hide the date entirely (`'off'`) even if the creator's locked `config.showDate` was `true`. `computeCaptionLayout()` treats the date as showing only when `config.showDate && dateStyle !== 'off'`. When there's no date line, the caption is centered in the whole band rather than top-anchored — see "Caption vertical positioning" below. If a future request asks to lock the date format too, or to let recipients edit more than that, the config shape and the `customizeDetails.style.display = 'none'` line above are the places to revisit.

**Background music.** `#musicToggle` and `#bgMusic` (a looping `<audio>` pointed at `sounds/lofi-loop.mp3`) are shown on every page load, main page included — not gated on `shared`. Default intent differs by page, though: **on** for a shared/customized template link, **off** for the plain main page (`musicUserDisabled = !shared`, set once `shared` is known, right before the initial `applyMusicIntent()` call). This is a page-load default only — it's not part of `config`/the shared URL, and the visitor can freely toggle it either way regardless of which default they landed on.

State is tracked as `musicUserDisabled` (a `let`, default `false` = "on") — an *intent* flag, not derived from `bgMusic.paused`. `updateMusicToggleLabel()` renders the toggle from this intent, so it correctly shows "on" immediately on load even before actual playback is technically possible (browsers block autoplay-with-sound until the visitor interacts with the page at all — expected, not a bug). `applyMusicIntent()` is the single place that both calls `play()`/`pause()` and refreshes the label; the toggle's click handler just flips `musicUserDisabled` and calls it.

Since default is "on" but autoplay is blocked pre-interaction, `tryStartMusicOnFirstInteraction()` listens for the visitor's first `pointerdown`/`keydown` **anywhere on the page** (not just the toggle) and starts playback then, unless `musicUserDisabled` is already `true`. It explicitly ignores clicks on `#musicToggle` itself and does not remove its listeners on such a click — the toggle's own handler already manages that click via `applyMusicIntent()`, and `pointerdown` fires before `click`, so without this exclusion the generic handler would start playback a beat before the toggle's own handler runs and (seeing `paused` already `false`) immediately reverses it. This was a real bug caught in testing, not a hypothetical — worth remembering if this logic is touched again.

Like `shutterAudio`, `bgMusic` is a plain `HTMLAudioElement`, not tied to the Web Audio API.

### Photo filter

`#filterSelect` (`default` / `bw` / `sepia` / `saturated`) applies to the 4 captured photos only, not the caption/date text or cut-guide lines.

**Applied via manual per-pixel matrix math (`getImageData`/`putImageData`), not `ctx.filter`.** The first version used `ctx.filter = 'grayscale(100%)'` etc. on the `CanvasRenderingContext2D` before each `drawImage()` call — this worked on desktop but **silently did nothing on some mobile browsers** (`ctx.filter` support is inconsistent there, notably older iOS Safari; when unsupported, setting the property is just a no-op with no error, so the filter dropdown appeared to do nothing). Fixed by implementing the exact color matrices the CSS Filter Effects spec itself defines for grayscale/sepia/saturate (`grayscaleMatrix()`, `sepiaMatrix(amount)`, `saturateMatrix(amount)` → `FILTER_MATRICES`), applied by hand via `applyPixelFilterMatrix()` after each shot is drawn. This works identically on every browser since it doesn't depend on any CSS Filter API support at all — verified by independently computing the same matrices in a separate test and confirming the rendered pixels match within rounding. Current amounts: grayscale 100%, sepia 75%, saturate 150% (mirroring what the old CSS filter percentages were).

Like `dateStyle`, `photoFilter` is a free post-capture choice (`filterSelect`'s `change` handler just sets it and re-runs `buildStrip()`) and is **not** part of `config`/the shared URL — same reasoning as "Recipient lockdown" above: nothing about it needs to be locked to the creator's template.

### Save to Photos

A plain `<a download>` link (`downloadStripPng()`) always lands in the device's Files/Downloads app on mobile — there is no web API that lets a page write directly into the system Photos/Gallery library, on iOS or Android, by design (privacy/security). The only cross-platform way to get there from a web page is the native share sheet's "Save Image"/"Save to Photos" action, via `navigator.share({files: [...]})`.

`saveBtn`'s handler therefore tries `navigator.share()` first when `canShareFiles()` says it's supported, and only falls back to `downloadStripPng()` when: sharing isn't applicable (desktop/laptop — falls back immediately, no share attempt), or `navigator.share()` throws something other than `AbortError` (a genuine failure). If the visitor cancels the native share sheet (`AbortError`), nothing else happens — canceling is a deliberate choice not to save, not an error to recover from with a forced fallback download.

**`canShareFiles()` gates on `isMobileDevice()` first, not just API support.** Several desktop browsers (macOS Chrome/Safari, tied into the OS share sheet, confirmed via direct testing) also implement `navigator.share`/`canShare` with files — checking support alone would make "Save to device" pop the native share sheet on desktop too, which is explicitly *not* wanted there (desktop/laptop should always just download to Files, like before this feature existed). `isMobileDevice()` is a `navigator.userAgent` check for `Android|iPhone|iPod|iPad`, plus an iPad-on-desktop-Safari heuristic (`Macintosh` in the UA + `navigator.maxTouchPoints > 1`, since iPadOS 13+ reports itself as a Mac in its UA string but exposes multi-touch, unlike a real Mac). Verified via UA/device emulation: a real desktop Chrome UA falls straight to `downloadStripPng()` even with Share API support stubbed in; emulated iPhone and Android UAs both correctly attempt `navigator.share()`.

`shareBtn` uses the same `navigator.share()` mechanism but has no download fallback (there's nothing sensible to fall back to for a "share with someone" action) and is kept as a separate button so intent stays clear to the visitor ("save this" vs. "share this"), even though on a capable device both currently open the same native share sheet under the hood.

`printBtn` also calls `canShareFiles()` (see "Print layout" below) — three buttons now share this one mobile-detection gate. If it's ever changed, all three need re-checking.

### Print layout

`printBtn` ("Print") is **split by platform**, on purpose — it does not use one universal mechanism:

- **Mobile** (`canShareFiles()` — which itself gates on `isMobileDevice()`, see "Save to Photos" above): shares a plain PNG of `buildPrintCanvas()`'s combined two-strip image via `navigator.share({files: [file]})` — the same mechanism `shareBtn` uses. Most mobile share sheets (iOS, many Android ones) offer a "Print" action directly for a shared image. Sharing an image hits the OS's native *photo*-print pipeline, not the "print this webpage" pipeline `window.print()` uses — this matters a lot in practice, since it's literally the pipeline these portable photo printers (e.g. the Liene M100) are designed around, and it handles borderless printing far more gracefully than printing a webpage does.
- **Desktop** (or any browser `canShareFiles()` says no to): uses `window.print()` via `@media print` CSS, same general shape as earlier in this project's history, with `#printSheet` populated with one `<img>` of `buildPrintCanvas()`'s output, sized to fill the full `4in × 6in` page with **zero margin** (`width: 4in; height: 6in;` — not shrunk with a safety buffer the way earlier revisions were).

**Why the split, and why desktop can now safely use zero margin:** two categories of mobile-specific bugs kept recurring when `window.print()` was used universally, both because printing *a webpage* goes through browser/OS machinery a page only has partial control over:
1. **Unprintable margins.** Mobile print pipelines (iOS AirPrint, Android print services) enforce their own margin even when `@page { margin: 0 }` is set — confirmed against the printer this was originally reported on (Liene M100: only needs ~1mm of its own bleed margin, proving the cutoff was never about the printer's own spec, but about the OS pipeline printing *a webpage*). Desktop's print-to-PDF/driver path is far more literal about honoring `@page { margin: 0 }` — this is *why* desktop can now safely go to true zero margin (no empirical buffer needed) once mobile is routed through a completely different pipeline (the share sheet) that doesn't have this problem at all.
2. **Injected header/footer.** Browsers printing a webpage add their own URL/date/page-count text — controlled by a "Headers and footers" checkbox in Chrome's print dialog on desktop (and in practice, `@page { margin: 0 }` tends to leave no room for the browser to draw it, so it's normally already suppressed there), but on mobile that checkbox is often not exposed to the user at all. Sharing a plain image on mobile sidesteps this entirely — there's no "webpage" being printed, so nothing injects header/footer text into an image.

**Print-specific margins around the two-strip block: `PRINT_TOP_MARGIN = 40`, `PRINT_SIDE_MARGIN = 20`, `PRINT_BOTTOM_MARGIN = 40`.** These are the literal, exact pixel distance from each dashed border line to the two-strip block's own edge in that direction — top of the block, the two *outer* left/right edges, and below the caption/date area. Distinct from `PADDING` (spacing within a single strip) and `CAPTION_PAD` (spacing within the caption band) — neither of those changed; these three constants add pure extra blank canvas around the *outside* of the whole two-strip block, specifically for the print formatting, and don't affect `buildStrip()`/the regular single-strip preview/Save/Share at all.

**Middle gutter, so each strip has equal margin on both of its sides.** Each strip's own photos/caption are already centered within its `stripW` (`PADDING` on both sides, see `drawStripContent()`). Originally the *outer* dashed border got `PADDING + PRINT_SIDE_MARGIN` of clearance from the photos, but the shared middle divider got only bare `PADDING` — no `PRINT_SIDE_MARGIN` — since the two strips were drawn directly adjacent (`0` and `stripW`). That made each strip look off-center: noticeably more whitespace to the sheet's outer edge than to the middle cut line. Fixed by inserting a `middleGutter = PRINT_SIDE_MARGIN * 2` gap between the two strips (second `drawStripContent()` call now offset at `stripW + middleGutter` instead of `stripW`) and centering the dashed cut line in that gutter (`coreOffsetX + stripW + middleGutter / 2`) — this gives the middle line the same `PRINT_SIDE_MARGIN` clearance on each side that the outer border already had, so every strip now has identical margin on its left and right.

**`PRINT_OUTWARD_NUDGE = 2.5`: a manual fine-tune, print-only.** On top of the equal-margins layout above, each strip's whole block (paper + photos + caption, not just the photos) is nudged this many px further toward its own outer edge — the left strip's `drawStripContent()` call uses offset `-PRINT_OUTWARD_NUDGE` instead of `0`, the right strip's uses `stripW + middleGutter + PRINT_OUTWARD_NUDGE` instead of `stripW + middleGutter`. The middle dashed cut line is *not* shifted by this — it stays exactly centered in the gutter, at `coreOffsetX + stripW + middleGutter / 2`, unrelated to the nudge. A prior attempt at closing this gap tried deriving the canvas height from a fixed `PRINT_PAGE_ASPECT` (so the exported PNG's own aspect ratio always matched the physical page exactly, avoiding `object-fit: contain` letterboxing) — reverted in favor of this simpler, purely visual per-strip offset.

Implementation: `buildPrintCanvas()` sizes its canvas as `coreWidth + PRINT_SIDE_MARGIN*2 + inset*2` by `coreHeight + PRINT_TOP_MARGIN + PRINT_BOTTOM_MARGIN + inset*2` (`inset = 5`, the existing canvas-edge-to-dashed-line distance, unrelated to these margins; `coreWidth = stripW*2 + middleGutter`), fills the whole thing paper-white first (the margin/gutter areas are outside what `drawStripContent()` paints), then `ctx.translate(inset + PRINT_SIDE_MARGIN, inset + PRINT_TOP_MARGIN)` before the two `drawStripContent()` calls (offsets `-PRINT_OUTWARD_NUDGE` and `stripW + middleGutter + PRINT_OUTWARD_NUDGE`) — a translate rather than passing more parameters into that shared function, so `buildStrip()` (which also calls it) needs no changes and can't be affected by anything here. Verified via direct coordinate sampling (not edge-detection scanning, which kept getting confused by the dashed line's own dash/gap pattern along its length in earlier attempts) — sampled specific computed pixel coordinates just inside vs. just outside each margin region and confirmed white/non-white as expected in all four directions, plus confirmed the canvas's overall pixel dimensions match the formula exactly.

The regular single-strip preview (`buildStrip()`/`#stripCanvas`, shown on-screen and used for Save/Share) has no outer `PRINT_SIDE_MARGIN` or `PRINT_OUTWARD_NUDGE` concept at all — just the same `PADDING` on both sides plus `ctx.textAlign = 'center'` for the caption — and is unaffected by any of this.

**History: this went through two other designs before landing here — self-generated PDF, then platform split.** A previous version generated a standalone PDF via a vendored `jsPDF` library (`jspdf.umd.min.js`, since removed) and either downloaded it or opened-and-printed it in a new window, specifically to sidestep the two mobile bugs above by not printing a webpage at all. That worked reasonably on desktop but was never confirmed reliable on mobile (iOS Safari's user-activation model may not survive `window.open()` regardless of timing — a platform restriction, not a bug that more code could fix) and added a heavy (~420KB) dependency. Replaced with the current design once it became clear that routing mobile through the *share sheet* (already-verified-reliable, since `shareBtn` already used it) was both simpler and more likely to actually work than fighting `window.print()`/a new-window PDF viewer on mobile — and removes the PDF dependency entirely, since neither platform needs a PDF anymore.

Verified via Playwright with the desktop UA (`isMobileDevice() === false`): `window.print()` is called with the print-sheet image fully decoded first. Verified via iPhone emulation (`isMobileDevice() === true`): `window.print()` is **not** called; `navigator.share()` is called instead with exactly one PNG file matching `buildPrintCanvas()`'s combined double-width dimensions (confirmed by comparing pixel dimensions against the single-strip canvas). Could not verify the actual native share sheet or print dialog UI from headless automation — same category of limitation noted elsewhere in this file for mobile-specific behavior.

### Caption vertical positioning

`drawCaptionLines()` has two distinct layout modes, chosen by whether a date line is present:

- **Caption + date** (two lines): top-anchored, starting at `top + CAPTION_PAD` with `textBaseline: 'top'`. The caption gets a small `+4` nudge down for visual balance above the date line beneath it — a hand-tuned constant, not derived from a formula.
- **Caption only** (no date): the caption is instead vertically centered in the *entire* white-space band (`top + layout.captionH / 2`) using `textBaseline: 'middle'` — the canvas's own baseline handling, not a hand-computed offset, so it stays correct regardless of font metrics. Combined with `computeCaptionLayout()` keeping `captionH` the same whether or not the date shows (see above), this means: same overall strip height either way, caption just recenters into the (now emptier) band when the date is off.

An earlier attempt at this used a single top-anchored formula with a hand-picked offset (4 vs. 6) to approximate centering/consistent-padding for the no-date case — abandoned in favor of the `textBaseline: 'middle'` approach above, which is both simpler and exactly correct rather than approximately tuned. Verified centering empirically: ink center within 3px of the band's true center.

### Mobile-specific details already handled
- `playsinline muted autoplay` on `<video>` — required for iOS Safari to render the camera feed inline instead of forcing fullscreen.
- `viewport` meta tag for correct scaling.
- `facingMode: 'user'` requests the front camera by default, with `#flipCameraBtn` to switch to `'environment'` (back camera) — see `startCamera()`/`initCamera()` above. The button only appears when `enumerateDevices()` reports more than one camera, so it stays hidden on typical single-webcam laptops.

## Known issues / dead code (as of 2026-09-14)

- `#retakeBtn` — rendered in HTML, referenced in JS (`retakeBtn.style.display = 'none'` in `runSession`), but **no click handler is ever attached and it's never shown** (`display:none` is its only state). Effectively vestigial. If "retake mid-session" is a wanted feature, this is the hook to wire up; otherwise it can be deleted.
- `#workCanvas` — declared, grabbed via `getElementById`, never read or drawn to anywhere else in the script. Looks like leftover scaffolding from an earlier compositing approach. Safe to remove unless a future feature needs a scratch canvas.
- `buildStrip()`'s `stripH = PADDING * 2 + photosH + layout.captionH` reserves an extra, unused `PADDING` (30px) worth of blank space at the very bottom of every exported strip. This is a leftover from before the caption band existed, when `PADDING * 2` correctly meant "top margin + bottom margin around the photos" — once the caption band was appended after that bottom margin, the caption's own `CAPTION_PAD` became the real bottom padding, and the outer `PADDING` contribution should have dropped to a single `PADDING` (top margin only). Not fixed here since it wasn't what was asked (a specific "keep bottom padding consistent" request was about the caption/date offset, not this) and removing it would visibly shrink every exported strip by 30px — flagging it rather than changing behavior unrequested.

## Considered but not built

**Video strip export** (2026-09-14): recording each of the 4 shots as a short video clip instead of a still, then compositing all 4 into one combined video laid out like the photo strip (4 stacked panels playing back together), with a "save video" option alongside the existing photo save. Technically possible — `MediaRecorder` to capture each clip, then play all 4 back into a shared canvas positioned the same way `buildStrip()` lays out photos, and re-record *that* canvas via `canvas.captureStream()` into the final combined file.

Not pursued for now: the output format tradeoff was the sticking point. `MediaRecorder` support for `.webm` is solid across browsers, but `.mp4` recording is inconsistent — notably weak on iOS Safari — so a client-side-only implementation would most reliably produce `.webm`, which doesn't play as universally on mobile (previews poorly in iOS Photos/Messages compared to a photo or real `.mp4`). Getting genuine `.mp4` output client-side would mean pulling in a heavy WASM encoding library (e.g. ffmpeg.wasm, several MB), a real architecture shift for what's currently a zero-dependency static site (see the React-vs-vanilla-JS decision and the "Custom template sharing" design choice above — this project has consistently favored staying lightweight over adding capability that requires heavier tooling). Decided the complexity/format tradeoff wasn't worth it right now. If this comes back: the design sketch above is the starting point, and the deciding question is still the same one — is `.webm`-only good enough, or does mobile-compatible `.mp4` matter enough to justify the dependency weight.

## If this grows

Reach for a framework/build step only if the project actually grows beyond a single screen — e.g. a gallery of past strips, multiple routes, or shared state across views. (A settings/theme picker alone did *not* require this — see "Custom template sharing" above, done with plain URL-encoded state.) A lighter first step than full React would be Vite + vanilla TS to get a dev server and type-checking without adopting a component framework. Until then, keep it plain static files (plus small vendored dependencies where justified) — it keeps load time minimal, which matters more than usual here since it's a mobile-first camera app.

If arbitrary custom frame *image* uploads become a requirement, that's the point where minimal serverless storage (no login, just an upload endpoint + object storage + short-ID lookup) becomes the right next step — see "Custom template sharing" above for the fuller tradeoff.

## Working conventions for this repo

- Keep it plain static files (`index.html` + `style.css` + inline JS) unless there's a concrete reason to split further (see "If this grows"). CSS was split out of `index.html` into `style.css` (2026-09-16, at the project owner's request) — a plain `<link rel="stylesheet">`, no build step, and confirmed to still load correctly both over HTTP and directly via `file://` (Playwright-verified both ways). JS stayed as a single inline `<script>` block since only the CSS split was requested.
- No build step should be introduced without discussing it first — the zero-dependency, drop-in-a-static-host nature of this repo is a deliberate feature, not an oversight.
- When editing capture/compositing logic (`captureFrame`, `buildStrip`), test on an actual mobile browser (iOS Safari in particular) — front-camera aspect ratios and `playsinline` behavior vary more there than on desktop webcams.
